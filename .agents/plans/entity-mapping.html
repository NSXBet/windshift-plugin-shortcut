2 · The workspace question

Decision (locked): a Shortcut Team is never a Windshift Workspace. Shortcut teams are functional units for ticket handling and scheduling — org grouping with no access semantics; Windshift workspaces are the access/collaboration boundary (own board, item and collection scoping). Team→workspace 1:1 manufactures access walls that don't exist upstream and resolves only indirectly via project.team_id — many workspaces, mostly empty.

Candidate models

Model Workspace count Pros Cons
A · Single workspace
everything into config.workspace_id		 1 (operator-chosen) Simplest; already implemented (workspace_mode:"single"); no workspace_upsert calls; no permission edge cases. Project/team context lives only in project_name + labels; one big board.
B · Workspace per project
Shortcut Project → Windshift Workspace — chosen (v0.4.0)		 1 per project Projects are the real work containers in Shortcut; board contents match what users see in Shortcut. Live-data backed: nsx-bet has 6 projects forming a real product partition (Aviator, E-Sports, Infra, New Platform, Bugs, New Features). Stories moving projects change workspace (re-upsert churn); epics need a separate central home.
C · Workspace per team, shared by its projects
current per_team		 1 per team Board per team mirrors ticket-handling groups. Invalid rationale — teams carry no access semantics; superseded by locked decision. Teams ≠ work units; empty workspaces for org-level teams; rejected-by-core handling already shows friction.
D · Workspace per workflow
Workflow → Workspace, project as section		 1 per workflow Workflows own the states, so status names resolve consistently inside one workspace. Unusual axis; mixing projects in one board.

Decision (locked, v0.4.0)

B (per-project) is implemented. Live-data review overturned the single-workspace recommendation: the nsx-bet org's real structure is project-partitioned (6 projects, one shared workflow), so workspaces mirror the genuine product partition instead of flattening it. workspace_mode:"per_project" resolves each story's workspace from its Shortcut project via workspace_upsert; epics land in the central workspace_id (all 2484 are team-less, org-level). single remains the default for greenfield installs.

  • per_team removed in v0.4.0 — C is rejected outright on both semantics (teams carry no access/partition semantics) and live data (one giant + empty shells).
  • Epic↔story parent links verified cross-workspace-safe: core resolveParentItemID resolves mappings globally, no same-workspace constraint.
  • Re-homing existing items: switching modes mid-flight leaves previously synced items in their old workspace (migration decision, out of v1 scope — state reset + re-sync is the lever, documented below).

3 · Implementation plan

Ship the sync with single-workspace only

Finish the in-flight stability work (epic-payload streaming, budget pause semantics, incremental cursor checkpoints) with workspace_mode:"single". Validate end-to-end against the live org: catalog (epics) → stories → comments → sweep.

Carry team identity as data, not structure

In single mode, append a team:<slug> label (find-or-create) to each item so a future move to per-project or per-team workspaces doesn't lose the grouping. Add team_id/team_name to item_upsert request only as labels — no core wire change.

Per-project workspaces (v0.4.0 — done)

resolveWorkspace re-keyed from team_id to project_id; epics pinned to workspace_id; per_team mode removed. Core grew two things: workspace_upsert now carries an external_kind ("team"|"project") so team and project ids can't collide, and plugin guests get the real host walltime + monotonic clock (wazero's default is a fake 2022-01-01 clock, which silently froze the sync watermark and disabled the tick budget). E2E harness covers created / fallback / rejected workspace paths. Live deploy: admin → Integrations → Shortcut Migration — verified importing with real 2026 windows; SC-PROJECT-* workspaces created on demand. Fallback bucket = projectless stories (project_id: null, the SRE/queue-workflow tickets).

Migrate if/when a second mode ships

Items already carry external_kind/external_id in shortcut_sync_items, so re-keying workspaces is a delete-and-resync (tombstone + fresh catalog), not a data migration. Document the operator runbook in the plugin README.

4 · Open questions

QuestionWhy it matters
Should epics live in the same workspace as their stories? Under model B/C a story's parent epic may resolve to a different workspace — cross-workspace parents need a core decision.
What happens to a story that moves project (→ workspace) mid-window? item_lookup finds the mapping, update path keeps the old workspace. Needs either a workspace-moved tombstone or core support for workspace change on update.
Comment author = actor_user_id always — keep? Shortcut author ids don't map to Windshift users; current behavior (single actor, suppressed notifications) is the safe default. Revisit if user mapping ever becomes available.
Do we ever sync Collections (e.g. mirror Shortcut's saved filters / epics views)? Collections are saved QL queries, not data. A v2 could create one static collection per Shortcut epic (external_id = "<epic-id>" filtered by label), but that needs a new plugin host function — out of scope for v1 and pointless until the workspace model (A/B/C) is settled.
